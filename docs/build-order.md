# Build order

What is not built, and what each piece waits on. Every item is designed in the doc that argues for it, and this page links there rather than restating it — the order is the part that lives nowhere else, and an item whose design drifts from its home page would otherwise have two authorities.

An item is listed here only while it needs a slice of its own. Anything fixable where it was found is fixed there instead.

The database owns the work: one row per order, holding its stable id, title, one-sentence statement, priority, hold and status, which `dim order ready` reads and `dim order add` writes, keyed on the repo's own `owner/repo`. This page owns the argument for each piece of work, and an item argued here carries the same id as the order built from it.

An order is queued when it is ready to be built, so what waits here is what is not. Priority decides which queued order is taken first, and a hold on the row is what keeps one until the owner releases it.

## The gates the skill still stands in for

Every rule below is written in [`dim-factory`](../skills/dim-factory/SKILL.md) today, which means it holds when the skill was read and not otherwise. Each item here is a mechanism that holds it either way, and the instruction it replaces is deleted from that file in the same slice — a rule a gate holds is cut, not shortened ([`conventions.md`](conventions.md)).

- **Staging by sweep is refused** (`no-blind-staging`)**.** `git add -A`, `git add .` and `git add --all` stage whatever is in the tree, and the owner edits that tree while a builder works in it — so a sweep commits the owner's unfinished writing under a subject about code, and nothing says so until someone reads the log. It happened on 2026-09-20, to a `findings.md` section that landed inside `feat(order): a finding belongs to a review round`. The rule is machine-wide prose today and the shape is mechanical: a `PreToolUse` hook on `Bash` reads the command, refuses those three forms, and names the paths the caller could have staged instead. It denies through the hook payload while exiting 0, which is what keeps the invariant that a hook never fails a session. What it cannot judge is a path argument that is itself broad, so it holds the three literal sweeps and leaves the rest to the sentence.

- **`post-commit` writes the commit and its changed files** (`post-commit-records-files`)**.** Outside a build station turn, whose runner records both from `git show --numstat` ([`docs/factory.md`](factory.md)), `dim order commit` and `dim order file` are typed by a skill, so a run that skipped a line leaves an order whose diff is smaller than what it landed. `git show --numstat` already holds the paths and the added and removed counts.

- **`pre-commit` writes the check row it already runs** (`pre-commit-records-check`)**.** The gate runs the repository's declared check and throws the result away; outside a build station turn, whose runner records the check it runs in the check sandbox, `dim order check` asks a skill to retype it.

## The measurement comes before any ranking change

`q search` ranks by cosine, and `dim bench` now says how well: it answers roughly half the labeled questions and misses the rest outright ([`findings.md`](findings.md)). So a tuning below can be scored against that set rather than argued, which is the rule [`recall.md`](recall.md) sets for itself. What the set cannot yet say is whether cosine beats the keyword index it replaced, since only one of them is scored.

The corpus-native half of the measurement is built: `dim bench` scores a hand-labeled `retrieval.jsonl` by recall@k and nDCG@k through the queries themselves, and reports a first number ([`findings.md`](findings.md)). What is left:

- **The external set** (`external-benchmark`) ([`recall.md`](recall.md)). LongMemEval is what a published claim is made against, so it is the only way such a claim becomes checkable here. Its dataset adapters are the part that transfers from Acolyte's harness; the metrics were written here.

- **A corpus wider than one hand** (`wider-corpus`)**.** The labeled set is small and every question in it was written by one agent in one sitting, so it reports what that agent thought to ask. `handoff_link` pairs a handoff with the session that acted on it, which is a query and its known answer that nobody had to invent — drawing questions from there is what makes the set larger than an opinion. A session can carry as many questions as it holds passages, since `search` names a passage (`passage-refs`) and `bench` grades one ([`design.md`](design.md)).

## Waiting on that measurement

- **Reciprocal-rank fusion** (`rank-fusion`) ([`landscape.md`](landscape.md)). The borrow table carries the shape, including why it is not a drop-in.
- **A ledger of which guidance cuts measurement confirmed or rejected** (`guidance-cut-ledger`)**.** Append-only, written when a cut is decided by the runner. Distinct from the rejected-changes ledger [`evals-and-hooks.md`](evals-and-hooks.md) declines: that one records proposals turned down and is a multi-contributor artifact `git log` already covers, while this records what a measurement settled, which `git log` does not hold. It waits on the first measured cut — a ledger with no rows is the empty table that argument rejected.

## Waiting on a judgment only the owner can record

- **How a repository declares its isolation strategy** (`workspace-contract`)**.** The rest of the workspace and worker-environment contract is live: [`src/workspace.ts`](../src/workspace.ts) resolves the profile [`factory.md`](factory.md) defines, `dim wt` invokes the repository-owned setup and teardown hooks and keeps a worktree when cleanup fails, and a running order attaches those reports to `factory_order` evidence where `dim q order` reads them back. `factory.md` argues why nothing a repository writes today answers the isolation strategy. What is the owner's: the declaration that would, because it asks every repository to write something new, and with it the requirements that are not variables — containers, ports and disk.

- **A self-maintaining loop, in a repo that ships apps** (`self-maintaining-loop`)**.** Pick the fault worth fixing from the crash reports its own service collects, and run `dim-line-fix` on it, on a schedule. Most of it exists there already: a script groups faults by fingerprint with a count and will hand the same rows to a machine rather than a reader, and the repo declares its own check, so the `pre-commit` gate holds under a run nobody is watching.

  Two things are not built. The loop needs a memory of what it already attempted, and that cannot be derived — a subject is capped at fifty characters with no body, so a fault id cannot ride along in a commit. It belongs beside the reports, keyed on the fingerprint, which also yields the outcome signal this repo lacks: a fault that stops arriving from versions above the one it was fixed in.

  It lives there rather than here, because reading those reports needs the network and a credential, which the invariant at the top of [`src/cli.ts`](../src/cli.ts) refuses. What is the owner's: whether an unattended run pushes, or commits locally and leaves the work to be read.

- **Corrections as a source** (`corrections-source`)**.** `correction_label` holds no rows, so the source that would catch a reworded repetition is empty, and `q repeats` cannot see one either ([`findings.md`](findings.md)). `dim q candidates` narrows and `dim label` records; nothing here labels itself, by design.

## Active factory work

- **Queue-driven execution** (`factory-queue-loop`). **The operator currently receives an explicit order id and drives the lifecycle. The factory still needs to select ready work, invoke the operator loop and keep queue selection separate from station judgment, along with serialized integration and the queue-state enforcement around those transitions; independent orders may run in parallel only after those boundaries are made explicit. Scheduling is a later trigger for this same path, not a replacement for it. Prior art: branch `factory-queue-loop`, which reserves the next ready order under the lock and runs a bounded count of them through the order lifecycle. Prior art: branch `rebase-station-worktrees`, which rebases a station worktree onto the trunk and stops on a dirty tree, a detached head or a conflict.**

## Ready or waiting on another slice

- **A worker cannot reach another hand's credential** (`worker-credential-isolation`)**.** Both adapters give every station worker `dim`'s data directory with `--add-dir`, because a worker records its evidence through `dim`, and that directory holds `worker-credentials/`, where [`src/worker-credential.ts`](../src/worker-credential.ts) keeps each worker's token — the operator's included. A worker that reads the operator's file can act as the operator, and so can one that runs `dim operator`, which [`src/operator-command.ts`](../src/operator-command.ts) answers from the operator's active session with that same file. Denying that one subdirectory to the sandbox closes nothing on its own, since the database beside it is writable and a token digest can be written into it directly. What closes it is a worker that writes nothing under the data directory itself: its `dim` writes go through a process outside the sandbox that it cannot impersonate, so the directory can be denied to it whole, and that process refuses a worker every command that hands back a credential.

- **One path runs a station worker** (`one-station-path`)**.** `runOrderPlan` and `runOrderReview` each have a synchronous twin beside the live one, and the twins run workers through [`src/order-worker.ts`](../src/order-worker.ts)'s `runOrderStation` and [`src/harness-command.ts`](../src/harness-command.ts)'s `runHarnessCommand`. The CLI reaches only the live path, since `runOrderCommandLive` handles the three stations before anything reaches `runOrderCommand`, so the twins run only in tests, and each harness change has to be made twice and drifts where it is not: the synchronous path never stops a refused run, because it waits for the process to exit. Deleting the twins moves their tests onto the live path, where a few expected outcomes differ. The live station functions' fallback to `DEFAULT_HARNESS` can go in the same slice: the CLI always passes a harness, resolved from the flag or the operator's recorded session, so only a test reaches that fallback, and a required harness is what stops a new caller from getting Codex silently.

- **A value outside a closed vocabulary should not compile** (`closed-vocabularies`)**.** `Role`, `OrderStatus`, `Tier`, `WallStation` and `HookKind` are each a fixed set, and every place that has to prove a string is one of them writes the check by hand — [`src/factory-wall.ts`](../src/factory-wall.ts) does it twice, once for a status and once for a role, each throwing its own sentence. `unreachable(value: never)`, which Acolyte keeps beside an `invariant` in its own `assert.ts`, moves that to the compiler: a vocabulary that grows stops building at every switch that does not handle the new word, which is what makes an unhandled case impossible rather than merely caught. What does **not** come with it is a general `invariant(condition, message)`, the shape graphql-js keeps in `src/jsutils/invariant.ts`: it produces an error distinguished only by prose, and every refusal a caller can trigger here carries a code instead — `WorkerUnknown`, `FactoryStopError`, `OrderNotDone`, `RoutingError`, `HooksNotCurrent`. So `invariant` is for a fact about this code that no caller can reach, of which [`src/factory-wall.ts`](../src/factory-wall.ts) already has one standing as a comment — "a claim writes its own event in the same transaction, so an order row always has one" — and a refusal that reaches a person keeps its code.

- **What the factory wall still cannot show** (`wall-gaps`)**.** The board is live: `dim wall` serves a three-column stage page over a loopback WebSocket, with no control endpoints and no second state store, and a card opens into the item view (`item-view`) — that order's lifecycle and evidence, read from the tables `dim q order` reads ([`human-interface.md`](human-interface.md)). What the item view holds is what the record holds, so the plan an order was given and the Build artifact wait on the writers that section names. A card shows how long its order has been silent but not what counts as too long: a threshold has to come off the distribution of gaps between recorded events, and the record holds too few to draw one. The rail in [`src/wall-item.ts`](../src/wall-item.ts) and the card both need a mark for `moved`, the station-move event: without one an order that has just reached another station reads as having no news. What else it cannot say: a worker's name is derived by [`src/worker-name.ts`](../src/worker-name.ts) from its agent id, so editing that word list silently renames every worker that ever ran — a durable `agent_id → display_name` table is what makes a name a fact rather than a function. A card names no project, so one board cannot carry work from more than one repo. And no operator record exists at all, so the wall cannot say which harness is driving the floor; [`factory.md`](factory.md) designs that boundary and nothing implements it. Prior art: branch `operator-presence`, which records clock-in and clock-out per harness session in `factory_operator_presence` and shows it on the wall.

- **The factory retakes what failed** (`factory-retakes-failed`)**.** A failed order is work nobody is holding and nobody comes back to, so the four recorded failures sit where they stopped. Taking one again is the same act as taking a queued one, which is what makes this a selection rule rather than a mechanism. The bound is already stated in [`dim-factory`](../skills/dim-factory/SKILL.md): one item failing twice says the item is wrong rather than the attempt, so a second failure leaves it and the run moves on. It waits on a failed order staying claimable.

- **A harness-neutral factory scheduler** (`factory-scheduler`)**.** [`factory.md`](factory.md) defines the boundary: `dim` owns schedule state, due selection and run evidence, while Codex, launchd, cron or another host only invokes it. The first slice is live as persisted interval schedules with `dim schedule define|pause|resume` and `dim q schedules`; host installation, queue claiming and order execution evidence remain outside it.

- **A scheduled architecture review** (`scheduled-architecture-review`)**.** A read-only `dim-station-review` pass uses the architecture dimension over a coherent group of changes or a change that crosses a module, schema, queue or hook boundary. It reports responsibility, contract and dependency drift separately from tests and slice checks; the review runs when the queue presents that boundary, not on an arbitrary timer.

- **Running a formatter after an edit** (`format-after-edit`)**.** The `PostToolUse` path should identify edit operations, resolve the checkout from the event's working directory, and read the repository's declared formatter through `formatCommand`. It should run that command against changed paths before the next agent action, record the command, paths, exit code and output, and fail open so formatting cannot break a session. Acolyte's workspace-contract shape and `$FILES` placeholder are useful interface ideas; its underlying-tool detectors are not, because the command the repository declares remains authoritative ([`recall.md`](recall.md)).

- **The working-directory check** (`working-directory-check`)**.** Git aimed outside the session's own directory fails three times as often ([`findings.md`](findings.md)). A commit hook knows the repo it runs in and not the one the session belongs to, so only a hook on the tool call can compare them. Prior art: branch `working-directory-check`, which denies a Bash git call aimed outside the session's checkout from a `PreToolUse` hook.

- **The weakening guard** (`weakening-guard`) ([`evals-and-hooks.md`](evals-and-hooks.md)), which warns rather than blocks. Prior art: branch `weakening-guard`, which warns from a `PostToolUse` hook on `Edit` and `Write` when an edit adds a skip marker or drops assertions.

- **Undoing an agent's writes** (`undo-agent-writes`) ([`worktrees.md`](worktrees.md)), which records that something changed and commits on a later pass.

- **The tooling chain in `wake`** (`wake-tooling-chain`) ([`recall.md`](recall.md)), which is the half of the project tier the record answers rather than the manifest: which CLIs a repo is actually worked with, derived from the shell commands its sessions ran. The workspace profile now detects the project tools needed by a builder, including commands from mixed ecosystems. What remains is whether that full command profile belongs in `wake`; its value and token cost need a measurement before it arrives in every session.

- **Two small edit infidelities** (`jsonc-edit-fidelity`)**.** A comment trailing the last element of an array ends up labeling the entry appended after it, because the insertion point is the end of the previous element and not the end of its line. And an edited object in a CRLF file comes back with LF line endings. Both are `jsonc-parser` behaviors rather than mistakes here, on top of the path/text split (`jsonc-io-split`) already landed; neither loses a value, and neither has a caller complaining yet.

- **Each `dim` subcommand carries its own help** (`subcommand-help`)**.** Queries already do — `q list` prints from the registry — while `src/cli.ts` holds a written-out usage string beside its switch, so adding a command is two edits and a missed one is silent. The reader is an agent that takes the printed surface as the whole surface, so a flag absent from the listing does not exist to it. The shape is in [`landscape.md`](landscape.md)'s borrow table, including what not to take from it.

- **A slice cannot commit unchecked.** Held at the order rather than at the commit, with the definition of done in [`factory.md`](factory.md). A `pre-commit` hook knows the repo it runs in and not which slice it is looking at, which is what blocked this; an order is that unit, and `dim order stop <order> completed` refuses one whose check did not pass after its last commit or whose commits have not reached the trunk. What the gate cannot see is work committed outside a claimed order, which is why the read-only half of this pair still matters: [`dim-station-build`](../skills/dim-station-build/SKILL.md) and [`dim-station-review`](../skills/dim-station-review/SKILL.md) both launch their agents without write tools, after a reviewer reverted a builder's fix on the same day.

- **`q repeats` classifies meaning with a word list** (`repeats-meaning`)**.** A stopword set decides which phrases are filler, a regex decides what nobody said, and 400 characters decides sentence from document. [`findings.md`](findings.md) already measured it missing the one correction repeated six times across 29 sessions, so the replacement is meaning rather than a better list — which waits on `correction_label` having rows.

- **A schema edit announces itself, rather than being remembered** (`schema-version-derived`)**.** `SCHEMA_VERSION` is an integer someone has to bump, and `openDb` only refuses a database when that number moves; a widened check that nobody numbered leaves the guard quiet while every table stays as `CREATE TABLE IF NOT EXISTS` first made it. `rebuild` names the tables it drops, so a table added later, or one whose exception no longer holds, keeps whatever shape it was created with. Both halves want deriving rather than declaring: a version read from the schema text, and a drop list that is every table except an explicitly preserved few, each carrying the reason it is spared. What has to be settled first is the cost of that check on a database this size, since every command opens one, and whether a table added with nothing feeding it should force a re-read at all — the argument against a bump for that case is at the top of [`schema.ts`](../src/schema.ts).

- **A stuck-slice counter** (`stuck-slice-counter`)**.** A slice that keeps failing the repo's check and being re-attempted is invisible to the loop today. Ferment blocks a step after three starts without a completion ([`landscape.md`](landscape.md)); the record here spans sessions, so it can see a slice retried once per session across four, which a per-run state file cannot. The operator bounds itself instead, stopping on the second failure of one item inside a run and seeing nothing across runs.

- **The arm that says whether checking pays** (`checking-pays-arm`)**.** `finding` holds the rows and `q findings` reads them by dimension, so what is left is the join nobody can run yet: a finding's file against the later `fix:` commits that came back to it, slices checked against slices that were not. It waits on rows rather than on code, and building the comparison before there are rows produces the empty table the rejected-changes ledger was turned down for.

- **A refused finding is acknowledged before the work ships** (`refused-finding-ack`)**.** A refusal resting on whether a finding is true rather than on whether it matters is settled by a hand that neither wrote the code nor raised the finding — so it is an acknowledgement a gate waits for, not a third agent the builder decides whether to reach for. For a review finding this is built: the next round's reviewer accepts or contests the refusal, a contested one holds review approval with `ruling_pending`, and the owner's word is its own `refusal_decided` event ([`docs/workflow.md`](workflow.md)). What is unbuilt is the same hold for a refusal the build station's own checker drew (`dim finding`), which the record keeps and no gate reads.

- **Two label counts state a base that can include a label whose message is gone** (`label-count-base`)**.** `correction_label` carries no foreign key, so a label outlives a message whose transcript left the disk. The per-skill column in [`src/queries.ts`](../src/queries.ts) joins `message` and drops such a row, while the two scalars beside it count the table bare, so the denominator can exceed the column it introduces with nothing saying why. Which is right is the decision: join `message` in both and count only labels that still reach one, or keep the bare count and have `rebuild` report the labels whose message did not come back.

- **`q keywords` prints no ref, so no question asked of it can be scored** (`keywords-ref-column`)**.** `keywords` ranks by how many of the asked-for terms a message carries rather than requiring every one, which the AND-only door this replaced could not do — asked "benchmark recall known relevant questions ranking" on 2026-09-17, it returned nothing while the subject was sitting in the record, and it now does. What it still prints is `session` and `when` as separate columns, which name a message to a reader and identify none to a program, so `dim bench` reports every question asked of it unscorable (`src/bench.ts:146`) rather than scoring it. The fix is a `ref` column of the shape `search` prints — `<session-prefix>@<timestamp>` — and the benchmark's `refusal` learning that a query's refs come from the population that query searches, since today it refuses any ref naming a turn nobody distilled, a rule correct for `search` and wrong for a door that searches every message anyone said.

- **Whether the simplification pass in `dim-station-build` pays** (`simplification-arm`)**.** The step is built and every slice now carries it, so it spends on each one; nothing measures what it returns. What would answer it is an arm — slices run with the pass against slices run without — scored by whether a later fix commit came back to what each touched, which is the join `q fixes` reads by skill and would have to read by arm. Until then the step rests on the owner's own practice, which is a reason to build it and not a measurement.

- **The aimed simplification pass** (`aimed-simplification`), which is the different question: which code that no slice just touched has earned one, read off `q fixes`, `q rework` and `q exemplars` rather than off whatever is open. This is where the measurement in [`findings.md`](findings.md) applies. Two pieces follow rather than block it: the unmodified-tests rule as a hook, and a catalog of smells as one agent per smell with a fixed brief, of which only file length, parameter count and duplicate blocks are shapes a gate can hold.

- **Why files edited under `agents-md` draw four times more fixes afterward than before** (`agents-md-fix-rate`) ([`findings.md`](findings.md)), on the largest station sample measured. Nothing explains it, and it is the shape every other station was checked for and cleared of.

- **The generated conventions block** (`conventions-block`) ([`conventions.md`](conventions.md)), which that writer is the precondition for. Its first condition is now met — three gates exist and `doctor` reports a hook that is missing, stale or in a directory git does not read, and a checkout where the push gate cannot fire — and its second is not: `loop.md` requires each cut recorded as characters removed against the calls they would have stayed resident for, and the three rules cut from `~/.claude/CLAUDE.md` on 2026-09-17 were cut by hand and never measured. Do that measurement before generating anything.
- **A gate for US spelling, and one for banner comments** (`spelling-banner-gates`)**.** The two rules left in the conventions file that a mechanism could hold. Everything else there needs judgement and stays written ([`conventions.md`](conventions.md)).
- **Slice 1 of the eval runner** (`eval-runner-inventory`) ([`evals-and-hooks.md`](evals-and-hooks.md)): the trimmed arm and the rule inventory.
- **A guidance-file arm for that runner** (`guidance-file-arm`)**.** [`loop.md`](loop.md) names the boundary: a rule inside `~/.claude/CLAUDE.md` has no seam the runner can deliver a trimmed version through, so a guidance cut is decided by reading. An arm built as a whole config directory is what closes it, and a trimmed surface has to be unlinked and written fresh inside the arm — writing through the symlink edits the real guidance, and only a test that reddens on that keeps it true.
- **An index over code by meaning** (`code-meaning-index`)**.** `prior-art` matches a path fragment, so a concept whose file is named for its domain is invisible to it — `lexer` returns nothing across 22 repos while `acolyte/src/log-parser.ts` is on disk ([`findings.md`](findings.md)). `q search` is semantic but covers only the text a person distilled. What is missing is the question "have we solved this shape before" where the shape is not in the filename. A ranking change can now be scored rather than preferred, so what this needs is questions of its own: `dim bench` grades what a query prints, and no query prints a file path as a ref today.
- **Extracting the toolchain that repeats** (`toolchain-extraction`)**.** Three of the drifted scripts are orders this repo already does once, so that part is deleting forks ([`findings.md`](findings.md), [`README.md`](../README.md)). The `mise` and env handling across five checkouts is the part that has to be built.

- **Intake sources beyond an operator request** (`dim-add-adapters`)**.** [`dim-add`](../skills/dim-add/SKILL.md) turns a natural-language request into one attributed `dim order add` row. File and issue-tracker sources still need adapters that preserve the same order identity, request detail, and attribution without making intake a planning station.

- **Stalled-attempt detection and retake policy** (`execution-state`)**.** The queue projection and station-attempt history are now separate: `factory_order.status` remains the queue's answer, while append-only `factory_order_attempt` rows record each claim as `running` and its explicit handoff or failure as `succeeded` or `failed`. What remains is detection for a worker that dies without recording a finish, plus the policy that lets the operator retake that work. Those decisions belong here rather than in the current claim path because no silence threshold or retake rule is live yet.

- **A rebuild says what a rename would cost the first-party rows** (`rebuild-carries-renames`)**.** "A schema change is `dim rebuild`, not a migration" holds for every table read back from a source and not for the factory's own, which [`src/sync.ts`](../src/sync.ts) saves verbatim and writes back. The restore keeps only the columns the new table still has, so a renamed column is dropped from the row on its way through: where the new column is `NOT NULL` the insert fails and the rebuild stops, and where it is nullable the value is gone with nothing said. Renaming `factory_order_finding.recorded_at` to `raised_at` on 2026-09-20 hit the first of those, and the rows had to be deleted by hand before a rebuild would run. What is missing is the rebuild reading its saved rows against the schema it is about to write and naming every column it cannot place, before it drops anything — a refusal a person can act on, rather than a constraint error partway through or a silent loss. The repair is the owner's to choose per rename; what the tool owes is the list.

- **A bad habit becomes an order** (`diagnosis-loop`)**.** The corpus already answers which files an agent had to come back to, where the owner pushed back, and what a checking agent raised — `dim q fixes`, `dim q rework`, `dim q findings` and `dim q corrections` each read a slice of it. What none of them does is close: a reader sees a pattern, decides it matters, and that decision lives in a conversation. The smallest closure is one act — a cluster of like events becomes a queued order carrying its provenance, so the reason the work exists is the rows that produced it rather than a memory of noticing. From there the same rule the gates follow applies to the loop itself: repeated manual inspection is a candidate for a query, a fixture, or a gate, and what the events cannot decide stays a judgement instead of being automated into a guess. A prescription that would change a rule or a gate is governed — bounded in scope, carrying the evidence it rests on, verified, and released by the owner — because a loop that rewrites its own gates without that is a factory grading its own homework, which is the shape `self-maintaining-loop` has to avoid rather than inherit. What it is measured by is accepted outcomes, stability, rework and recovery time, and how much of the owner's attention a run spends; never tokens, lines, commits or how long a run went unattended, for the reason [`findings.md`](findings.md) already gives under "Effort does not grade the work". Which operator, model and role performed an attempt belongs on the attempt, because a diagnosis that cannot say which harness produced a habit cannot prescribe anything. One thing does not transfer: a factory-supplied behavioral fixture would be the factory deciding what a project's externally observable correctness is, and [`factory.md`](factory.md) settles that the other way — the host proves what it can read, the project declares what only it knows. So the lever is making a repo able to declare a behavioral check beside its unit check, not shipping one.

- **The shortest path that controls the risk** (`artifact-chain`)**.** Plan approval and `change-summary` are each a hold on an artifact, and the contract they share is worth stating once rather than twice. Three rules, taken from HumanLayer's separation of workflow phases. Correcting a short artifact costs less than correcting a large diff, which is the whole argument for planning before building and the reason a plan is worth a wait. An approval attaches to the artifact carrying the decision and never to a state meaning the agent is ready, so a hold releases one identified revision of one plan and a later revision is unapproved until it is approved in its own right. Each revision is a separate immutable row, because a replacement document nobody can identify loses why the decision moved. What follows from the first rule is that no order runs every phase by default: the path is chosen for the risk it carries, and a fix whose triage already produced a failing test has its plan in that test. Two phases HumanLayer separates are deliberately not taken. Research is not an artifact here — scoping against the record is the planner's own first act, and a separate hand to do it would return a conclusion whose grounds the planner then could not check. And an implementation outline distinct from the plan is a second authority on one question, which is the drift a single versioned plan exists to prevent. HumanLayer's hosted control plane, its PR-shaped completion, its Markdown task files and its Slack and email approval channels stay adapter ideas: the local database is the source of truth, and done keeps the meaning [`factory.md`](factory.md) gives it — the project's own check, answered findings, docs moved with the behavior, integration recorded, and the owner's judgement — never a clean exit or a moved ticket.

- **What the change does, read before it lands** (`change-summary`)**.** The operator approves a plan before the build and sees commits after it, and between those two the only description of what an order actually did is its diff. A Build artifact the builder writes alone is the shape that let a builder pass its own review: an artifact of a change by the hand that made it cannot be told apart from an artifact of the change it meant to make. Two hands write it instead, and the pair is the point — the builder states what each slice set out to do, the reviewer states what the diff does, having already read it cold for findings, and the operator reads them side by side where a mismatch is the signal rather than something to be caught by re-reading the diff. It costs one extra passage from a reviewer that is already reading, it holds `dim order ship` the way plan approval holds the build, and it shares the wall's writer with both.

- **The wall asks for the owner when it needs them** (`wall-notifications`)**.** A board only works while someone is looking at it, and the two states that need a person — `held` and `failed` — are exactly the ones that arrive when nobody is. The wall already marks both, so what is missing is the signal leaving the page. Pair it with the silence threshold `wall-gaps` names, which cannot be drawn until the record holds enough gaps between events to take a distribution off.

- **A new worktree installs what the manifest says it needs** (`worktree-install`)**.** A worktree is a fresh directory with no dependency tree in it, so the first thing any check does there is fail for a reason that has nothing to do with the work. [`factory.md`](factory.md) leaves this to a setup hook the repository writes, which is right for what only the project knows — services, ports, secrets — and is a hook every ordinary repo has to write before it can be worked at all. The package manager is not one of those things: it is in the lockfile and the manifest, on disk, free to read. Installing from what was detected covers the ordinary repo with nothing written, and the hook stays for everything a manifest cannot prove. It shares its reader with `manifest-readers`, and Acolyte's workspace handling is the prior art to read before designing any of it, being where the detect-or-declare rule came from in the first place.

- **The check is read off whatever manifest the repo keeps** (`manifest-readers`)**.** [`src/workspace-commands.ts`](../src/workspace-commands.ts) reads a check from a `package.json` script, a `mise.toml` task or a `Makefile` target, and stops there. A Dart repo stating its check in `pubspec.yaml` therefore declares nothing the gate can see: `dim check-command` prints nothing, the commit gate exits 0 over every commit, and the factory refuses the repo because a slice that cannot be checked cannot be committed. The rule this follows is the one [`factory.md`](factory.md) already records from Acolyte — detect what the host can prove from the workspace, declare what only the project can know — and a check is provable, being written in a file the repo tracks. So the answer is a reader per manifest rather than a declaration: `pubspec.yaml` first, since it is the one that bites, then whichever ecosystem arrives next. That the set grows is the cost of the manifests being the authority, and a repo asked to restate on paper what it already states in a file is the failure the rule exists to prevent. What makes it the right cost is the price of the alternatives: a reader opens one file and is exact, spends no model call and cannot disagree with what the repo runs, while a declaration goes stale the first time a script is renamed and an inference would be a guess bought with tokens. Prior art: branch `workspace-pubspec-commands`, which reads `pubspec.yaml` `scripts:` as workspace commands.

- **A check reads as green or not, never as a command** (`check-reads-as-a-bit`)**.** What the owner needs off a check is whether it ran and whether it passed. The command that carried it — `bun run verify (0, 607 tests, worktree suite 40/40)` — is a string the board and the order report both spend a column on, and it says the same thing on every order in the repo, because a repo declares one check. It stays in the record, where a query can ask which command vouched for a commit and a repo that changed its check can be told from one that did not; it comes off the surfaces the owner reads, where a mark carries the bit and a repeated command carries nothing. It goes with `order-report-columns`, which is the same cell.


- **An order's report read as columns rather than as one cell** (`order-report-columns`)**.** `dim q order` packs the priority, the hold, the station and the stop reason into a single `evidence` cell joined by ` | `. It is a table inside a table: a reader splits it by eye, nothing can sort or filter on a part, and the cell is wide enough to push every other column out of shape. Each fact is its own column, sized to what it holds, and the separator goes with the packing rather than being swapped for a nicer one.

- **Worktrees under a directory no tool owns** (`agents-worktrees-dir`)**.** [`src/wt-command.ts`](../src/wt-command.ts) puts every task worktree under `.claude/worktrees/`, which names one harness inside a repo that is worked by two. The skills already resolved this the other way — they link into `~/.agents/skills` and only then into each tool's own directory — so `.agents/worktrees/` is the convention this repo already holds elsewhere. It reaches the command, the four paths recorded against existing orders, and anything ignoring the old directory.

- **A moved checkout reads as a second repo** (`moved-checkout-identity`)**.** `repo_commit`, `repo_file` and `commit_file` are keyed on the git toplevel, which is where the checkout happens to sit. Move it and `dim sync` writes the same repo's commits under the new path beside the rows already there, so one repo reads as two and every per-repo number splits across both until someone notices. A rebuild heals those three, since they are re-read from wherever the repo now is. The identity that survives a move is already recorded — `repo_commit.label`, the `owner/repo` the remote gives, which the schema calls the identity a worktree shares — so this is keying the joins on what is durable rather than adding anything. It is the query side of the identity mistake an order's own row no longer makes.

- **A session can leave a message for another that is running** (`session-messages`)**.** `dim` reads every Claude and Codex session on this machine and writes into none of them, and Claude's own messaging reaches only Claude sessions, so two operators working one repo from different harnesses coordinate only through the owner copying text between them. On 2026-09-25 three unlanded branches each claimed schema version 57, one of them had already rebuilt the live database, and the sessions that made them had no way to learn of each other. The message belongs in the record, addressed to a session and written by the session that sends it, which keeps it first-party and readable after both have ended. Delivery is the part to establish first: a message reaches a running agent only through a hook that can place text in front of it mid-session, and which event does that in each harness, and at what cost on a hook that fires every tool call, is not yet known here. The `SessionStart` context `wake` already answers with covers a session that starts after the message was sent, and nothing else.

- **What a tracker settled and what it did not** (`tracker-prior-art`)**.** The queue converges on shapes an issue tracker already has — items, statuses, a transition log, dependencies, a board grouping statuses into columns — and diverges for reasons that are worth stating once: statuses are a `CHECK` a gate reads rather than a workflow anyone edits, stage is derived in [`src/factory-wall.ts`](../src/factory-wall.ts) rather than stored per column, and transitions are evidence a check can re-walk rather than an activity feed. Written as the reasoning it is, citing what a named tracker actually models at a pinned revision. No benchmark was run, and a page claiming one would be the kind of sentence nobody can check later.

## Deliberately not next

- **The routing tier** (`routing-tier`) ([`evals-and-hooks.md`](evals-and-hooks.md)). Revisited only if telemetry shows misroutes that fixing by reading did not close.

- **A markdown writer that replaces a heading's byte range** (`heading-range-writer`)**.** The property it exists for is real — a `##` inside a fenced code block is not a heading, and only an AST holds that. But its only caller is the generated conventions block, which waits on a measurement nobody has taken, so building it now produces a tested module with nothing to call it.
